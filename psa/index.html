Google Cloud Networking Note

PSA / PSC 구성 시 꼭 알아둘 핵심 포인트

Private Services Access와 Private Service Connect를 설계할 때 자주 헷갈리는 주제를 빠르게 비교하고, 실무에 바로 쓸 수 있게 정리한 참고 페이지입니다.

핵심 1

PSA는 VPC Peering 제약을 그대로 받으므로 대역 설계와 비전이성 확인이 우선입니다.

핵심 2

PSC는 멀티 VPC, 서비스 단위 통제, 명시적 endpoint 설계에 더 유리합니다.

핵심 3

NIC에 안 보인다고 PSA가 깨진 것은 아닐 수 있으니 Topology만으로 판단하지 않는 편이 안전합니다.

공식 문서 기준 메모

아래 비교표와 서비스별 range 표는 2026-03-26 기준 Google Cloud 공식 문서를 바탕으로 정리한 참고 자료입니다. 일부 서비스는 제품, 티어, 리전, 네트워크 아키텍처에 따라 요구 조건이 달라질 수 있으므로 실제 설계 전에는 해당 서비스 문서를 다시 확인하는 것이 안전합니다.

1) PSA 구성 시 주의사항

PSA는 내부적으로 VPC Peering 기반이므로 비전이성(non-transitive) 제약을 그대로 받습니다. allocated range는 현재와 미래 subnet, peered VPC, NCC spoke, custom static or dynamic route와 겹치지 않게 설계해야 합니다.

Google 서비스 기준 allocated range는 최소 `/24`, 권장은 `/16`입니다. 또한 service producer subnet은 소비자 쪽에서 직접 고를 수 없고, 기존 allocated range를 잘못 축소하거나 삭제하면 신규 subnet 생성이 막힐 수 있습니다.

2) PSA cache 메커니즘 (TTL, 재할당 패턴)

공식 문서에는 조정 가능한 `PSA cache TTL` 값이 공개되어 있지 않습니다. 문서상 동작은 캐시라기보다 producer subnet lifecycle에 가깝습니다.

기존 리소스는 기존 range와 subnet을 계속 사용하고, 새 range를 추가해도 신규 subnet 또는 신규 리소스부터 반영됩니다. old peering route가 잔존할 수 있으며, 예시로 Cloud SQL은 리소스 완전 삭제까지 최대 4일이 걸릴 수 있습니다. 실무적으로는 TTL보다 비동기 정리 지연으로 이해하는 편이 더 정확합니다.

3) Network Intelligence Center 사용성

`PSA가 붙은 서비스가 NIC에 보이지 않는다`는 현상은 일부 정상 동작입니다. Network Topology는 Google-managed services 연결을 보여주지만, Cloud SQL, Filestore, Memorystore 등 일부 서비스 트래픽은 표시되지 않을 수 있습니다.

Connectivity Tests도 Google-owned project 내부 세부 hop 대신 overall reachability 중심으로 보여줍니다. 따라서 PSA 점검은 Topology 단일 화면만 보지 말고 Connectivity Tests, PSA utilization, route 확인을 함께 수행하는 것이 안전합니다.

NIC에서 실무적으로 더 유용한 포인트: IP Utilization Analyzer 계열 insight

공식 명칭은 Network Analyzer의 `Private services access IP address utilization summary`입니다. Topology에 서비스가 잘 안 보여도, 여기서는 PSA range와 PSA subnet 기준으로 실제 사용 현황을 더 직접적으로 볼 수 있습니다.

  • 1. `PSA range prefix`, `PSA subnet prefix`, `PSA subnet region`, `PSA subnet service`, `allocation ratio`를 확인해 어떤 서비스가 어떤 대역을 얼마나 쓰는지 봅니다.
  • 2. Shared VPC라면 host project에서 이 insight를 확인합니다.
  • 3. `allocation ratio`가 50%를 넘기기 시작하면 allocated range 추가를 조기에 검토하는 것이 공식 권장입니다.
  • 4. `PSA subnet service` 이름 필드는 AlloyDB, Apigee, Cloud Build, Cloud SQL, Memorystore for Memcached, Memorystore for Redis, Vertex AI managed notebooks에서 채워집니다.

4) PSA 서비스별 Prefix IP range

`PSA는 무조건 /24`가 아닙니다. 서비스별로 요구가 다르고, Google 공통 allocated range 권장은 최소 `/24`, 보통 `/16`입니다.

예를 들어 Cloud SQL은 리전별 `/24` 단위를 사용하며, Memorystore for Memcached는 PSA allocated range를 `/24` 이상으로 권장합니다. 핵심은 소비자가 잡는 allocated range 크기와 서비스가 내부적으로 소비하는 subnet 크기를 구분하는 것입니다.

5) PSA vs PSC Best Practice

일부 추론이 포함되지만, 단일 VPC에서 Google-managed VPC-hosted service를 private IP로 연결하는 기본 패턴은 PSA가 더 단순합니다.

반면 다중 VPC, 다중 프로젝트 또는 조직, endpoint 단위 통제, producer-consumer 분리, Google APIs 또는 published service 접근이 필요하면 PSC가 더 적합합니다. Cloud SQL처럼 PSA와 PSC를 함께 쓰는 혼합 패턴도 가능합니다.

6) PSC의 network attachment vs service connection policy

둘은 모두 PSC 계열이지만 역할이 다릅니다. network attachment는 PSC interface용 리소스로, producer가 consumer VPC subnet에서 IP를 받아 연결되는 구조이며 connection preference가 attachment 승인 정책입니다.

반면 service connection policy는 지원되는 managed service가 consumer VPC 안에 PSC endpoint를 자동 생성하도록 돕는 자동화 정책입니다. 즉 `attachment = interface 연결`, `policy = endpoint 자동 생성`으로 구분하는 것이 적절합니다.

8) network attachment vs service attachment vs service connection policy 비교표

셋 다 PSC 문맥에서 자주 같이 언급되지만, 위치와 역할이 다릅니다. `service attachment`는 published service의 producer 측 리소스, `network attachment`는 PSC interface의 consumer 측 리소스, `service connection policy`는 managed service의 endpoint 자동 생성 정책으로 보면 정리가 쉽습니다.

항목 network attachment service attachment service connection policy
역할 PSC interface의 consumer 측 연결점 published service를 외부 VPC에 노출하는 producer 측 리소스 지원되는 managed service가 PSC endpoint를 자동 생성하도록 하는 정책
주 사용 시나리오 producer가 consumer VPC로 outbound 연결해야 할 때 consumer가 producer의 published service에 endpoint 또는 backend로 접근할 때 Cloud SQL 같은 managed service가 consumer VPC 안에 endpoint를 자동 만들 때
연결 방향 producer to consumer consumer to producer managed service to consumer endpoint automation

10) 짧은 메모

PSA cache 관련

공식 TTL 값은 문서에서 확인되지 않았고, 실제 운영상으로는 TTL보다 비동기 정리 지연을 더 중요하게 보는 편이 맞습니다.

NIC 해석 관련

Topology가 일부 Google-managed service 트래픽을 표시하지 않을 수 있으므로, 화면에 안 보인다고 PSA 문제로 단정하지 않는 것이 안전합니다.
